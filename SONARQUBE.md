# SonarQube analysis

SonarQube Cloud gives maintainers one view of code-quality and security
findings across the monorepo (#2248). Analysis is **report-only**: it never
blocks a merge or a release.

## Hosting

- **Service:** SonarQube Cloud, one project for the whole monorepo, bound to
  the `marcin-wosinek/fair-event-plugins` GitHub repository.
- **Analysis mode:** CI-based, from `.github/workflows/sonarqube.yml`.
  _Automatic analysis must be turned off_ in the SonarQube Cloud project
  (Administration → Analysis Method), or every commit is scanned twice and
  the CI scan fails.
- **Region:** EU (`sonarcloud.io`) unless the `SONAR_REGION` variable is set
  to `us` (`sonarqube.us`).

### Repository settings

| Name                 | Kind     | Value                                                               |
| -------------------- | -------- | ------------------------------------------------------------------- |
| `SONAR_TOKEN`        | Secret   | A SonarQube Cloud token with analysis permission on the project.    |
| `SONAR_ORGANIZATION` | Variable | The SonarQube Cloud organization key.                               |
| `SONAR_PROJECT_KEY`  | Variable | The project key, shown under the project's Information page.        |
| `SONAR_REGION`       | Variable | Optional. `us` for the US region; leave unset for the default (EU). |

Set them under Settings → Secrets and variables → Actions. The organization
and project key are not secret but live in variables, so they are not
hardcoded in `sonar-project.properties`.

### Token ownership and rotation

The token belongs to the repository owner's SonarQube Cloud account. Prefer
an organization-scoped or project-scoped token over a personal global one.

To rotate it: create a new token in SonarQube Cloud (My Account → Security),
replace the `SONAR_TOKEN` secret, re-run the workflow on `main` with
**Run workflow**, check that it succeeds, then revoke the old token. Rotate
it whenever its owner loses access or it may have leaked, and before it
expires.

## When analysis runs

| Event                                   | Result                                                  |
| --------------------------------------- | ------------------------------------------------------- |
| Push to `main`                          | Analyzed as the `main` branch.                          |
| Pull request to `main` from this repo   | Analyzed as a pull request against `main`.              |
| Pull request from a fork                | Skipped with a notice; the job passes.                  |
| Dependabot pull request                 | Skipped with a notice; the job passes.                  |
| Manual run (**Run workflow**) on `main` | Analyzed as the `main` branch.                          |
| Manual run on any other branch          | Skipped with a notice.                                  |
| Eligible run with missing configuration | The job fails and names the missing secret or variable. |

Every run writes a job summary saying whether analysis succeeded, failed or
was skipped and why, with a link to the dashboard for that branch or pull
request.

### Credential protection

- The workflow uses the `pull_request` trigger only, never
  `pull_request_target`, so fork pull requests and Dependabot never receive
  `SONAR_TOKEN`. They are skipped before checkout.
- The job has `contents: read` permissions, checks out without persisting
  Git credentials, and passes the token only to the pinned scanner step.
- The job installs no dependencies, builds nothing and runs no repository
  code; the scanner only reads sources. Event values reach shell steps
  through environment variables, never interpolated into the script.
- Third-party actions are pinned to a commit SHA. Update the scanner by
  replacing both the SHA and the version comment.

## Scope

`sonar-project.properties` is generated by `npm run sonarqube:config`
(`scripts/sonarqube.mjs`); do not edit it by hand. It derives the scope from
the root `package.json` `workspaces` list with the same production-source
rules as the [duplication report](./README.md#duplication-report):

- **Included:** each workspace's top-level PHP bootstrap files, `src/`,
  `php/src/` (the shared package) and `templates/`, limited to PHP and
  JavaScript (`.js`, `.jsx`, `.mjs`, `.cjs`).
- **Excluded:** `node_modules/`, `vendor/`, `build/`, `dist/`, `svn/`,
  `languages/`, `test-results/`, `playwright-report/`, test and fixture
  directories (`__tests__/`, `__mocks__/`, `__fixtures__/`, `fixtures/`,
  `e2e/`), `*.test.*` and `*.spec.*` files, generated `*.asset.php` and
  `*.min.js`.
- **Out of scope for now:** root tooling (`scripts/`, `bin/`, `tools/`),
  test code, and CSS.

The Repository validation CI job runs `npm run validate:sonarqube`, which
fails when the committed file no longer matches the workspaces. After adding
a workspace or a top-level plugin PHP file, run `npm run sonarqube:config`
and commit the result.

## Baseline

The first successful `main` analysis is the adoption baseline. Record its
run link and commit in issue #2248. Existing findings stay open for triage:
they are not bulk-marked accepted and need no cleanup to adopt the tool.
Pull request analysis compares a change against the analyzed `main`, so new
findings stand out from the baseline.

## Quality gate policy

- **Now:** report only. The `SonarQube analysis` check is _not_ required in
  branch protection and no release workflow depends on it. A failed scan or
  missing configuration still fails the job visibly; quality findings never
  fail it (the workflow does not wait for the quality gate).
- **Later:** enabling a mandatory gate on new code is a separate decision.
  It would mean waiting for the quality gate in the workflow
  (`sonar.qualitygate.wait=true`), agreeing on the gate's conditions, and
  adding the check to branch protection.
- **Coverage:** not imported yet. Producing and importing LCOV and PHP
  coverage reports is a follow-up decision.

## Troubleshooting

- **"Missing SonarQube configuration"** — set the named secret or variable,
  then re-run the job.
- **"You are running CI analysis while Automatic Analysis is enabled"** —
  turn off automatic analysis in the SonarQube Cloud project.
- **401 / "Not authorized"** — the token expired, was revoked, or lacks
  access to the project. Rotate it as above.
- **Project or organization not found** — check `SONAR_ORGANIZATION`,
  `SONAR_PROJECT_KEY` and `SONAR_REGION` against the SonarQube Cloud project.
- **A pull request shows no Sonar results** — check the job summary: fork
  and Dependabot pull requests are skipped by design.
- **`validate:sonarqube` fails** — run `npm run sonarqube:config` and commit
  `sonar-project.properties`.
